# Phase 15 — Backup & Restore Procedure

Status: **DONE** (documented; safely testable, not executed against live data as part of this phase).

## 1. What this covers

A repeatable procedure to back up and restore the **PostgreSQL database** that
stores all Saamu shop data (customers, orders, tailors, attendance, payroll,
payments, billing, expenses, income derivation and reports). This is the
authoritative data store: everything the ERP displays is derived from rows in
this database.

## 2. What is and is not included in a database backup

### Included (`pg_dump` custom-format dump)

- Every table in the `saamu_db` database: schema (tables, indexes, constraints,
  sequences) and all rows.
- User accounts, RBAC role flags, audit fields (`created_by`, `recorded_by`,
  status history) and all financial history (payments, expenses, payroll
  settlements, salary advances, invoice items).
- Sequences, so new invoice/order numbers continue correctly after a restore.

### Not included

- **Uploaded files** under `backend/media/` (currently not used by Version 1
  features). If media is ever added, back it up separately.
- **Static assets** under `backend/static/` (the built frontend and Django
  collectstatic output) — regenerated by `python manage.py collectstatic`.
- **The frontend build** (`frontend/dist/`) — regenerated by `npm run build`.
- **Environment configuration** (`backend/.env`) — secrets must be stored and
  backed up separately, never inside the database dump.
- **Logs** (`backend/logs/`).
- The database cluster as a whole (roles, global settings). Only the
  `saamu_db` application database is dumped.

## 3. Backup command

Uses PostgreSQL's native `pg_dump` in custom format. The dump goes **outside the
application source directory** — a dedicated backup folder such as
`D:\SaamuBackups` (never `D:\Projects\saamu\backend`).

Environment (from `backend/.env`): database `saamu_db`, user `postgres`, host
`127.0.0.1`, port `5432`. Password is prompted or supplied via
`PGPASSWORD`/`pgpass`; it is never embedded in the backup filename or the
committed documentation.

```powershell
# Set up the backup directory (once)
New-Item -ItemType Directory -Path "D:\SaamuBackups" -Force | Out-Null

# Backup with a timestamped filename (YYYY-MM-DD_HHMMSS)
$stamp = Get-Date -Format "yyyy-MM-dd_HHmmss"
& "C:\Program Files\PostgreSQL\18\bin\pg_dump.exe" `
  --host 127.0.0.1 --port 5432 --username postgres `
  --dbname saamu_db --format=custom --no-owner --no-privileges `
  --file "D:\SaamuBackups\saamu_db_$stamp.dump"

# Confirm the file was created and is non-trivial in size
Get-Item "D:\SaamuBackups\saamu_db_$stamp.dump" | Select-Object Name, Length
```

Notes:

- `--format=custom` is the recommended format: compressed, restore-able
  selectively, and it preserves types precisely.
- `--no-owner --no-privileges` keep the dump portable (the restore target is
  the same local `postgres` role, but this prevents absolute role references
  from breaking a restore on a differently-named role).
- A `PGPASSWORD` environment variable can be set once in the shell instead of
  typing the password every time. Never add it to a committed file.

## 4. Retention recommendation

- Keep daily backups for the current week plus at least one backup from a
  previous month.
- The naming convention (`saamu_db_YYYY-MM-DD_HHMMSS.dump`) already sorts
  chronologically, so a scheduled cleanup can simply keep the newest N files.

## 5. Restore workflow

### 5.1 Safe test restore (recommended, and the only kind to practice)

Never restore over the live shop database to "try it out". Instead, create a
throwaway database, restore into it, and verify:

```powershell
# Create a fresh test database
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --host 127.0.0.1 --port 5432 --username postgres --dbname postgres `
  -c "DROP DATABASE IF EXISTS saamu_restore_test;"
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --host 127.0.0.1 --port 5432 --username postgres --dbname postgres `
  -c "CREATE DATABASE saamu_restore_test OWNER postgres;"

# Restore the latest backup into the test database
& "C:\Program Files\PostgreSQL\18\bin\pg_restore.exe" `
  --host 127.0.0.1 --port 5432 --username postgres --dbname saamu_restore_test `
  --no-owner --no-privileges --clean --if-exists `
  --file "D:\SaamuBackups\saamu_db_2026-01-01_000000.dump"

# Verify row counts match expectations
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --host 127.0.0.1 --port 5432 --username postgres --dbname saamu_restore_test `
  -c "SELECT (SELECT count(*) FROM customers_customer) AS customers, (SELECT count(*) FROM orders_order) AS orders, (SELECT count(*) FROM billing_invoice) AS invoices;"

# Drop the throwaway database when done
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --host 127.0.0.1 --port 5432 --username postgres --dbname postgres `
  -c "DROP DATABASE IF EXISTS saamu_restore_test;"
```

Then run Django's integrity checks against the test database to confirm the
restored data is internally consistent:

```powershell
$env:DATABASE_NAME = "saamu_restore_test"
& python manage.py check
& python manage.py showmigrations --plan | Select-String "\[X\]" | Measure-Object   # all should be applied
```

### 5.2 Restore to recover the live database (only after a verified backup)

```powershell
# 1. Stop the backend process that is writing to the database.
# 2. Drop and recreate the live database:
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --host 127.0.0.1 --port 5432 --username postgres --dbname postgres `
  -c "DROP DATABASE saamu_db;"
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" --host 127.0.0.1 --port 5432 --username postgres --dbname postgres `
  -c "CREATE DATABASE saamu_db OWNER postgres;"
# 3. Restore the backup:
& "C:\Program Files\PostgreSQL\18\bin\pg_restore.exe" `
  --host 127.0.0.1 --port 5432 --username postgres --dbname saamu_db `
  --no-owner --no-privileges `
  --file "D:\SaamuBackups\saamu_db_<timestamp>.dump"
# 4. Verify, then restart the backend.
```

## 6. Safety rules

- **Never test destructive restore operations against the live shop database**
  without a verified backup and a controlled recovery plan.
- A backup is only trusted after a successful **test restore** (section 5.1)
  has been verified at least once on the machine where recovery would happen.
- Keep backups outside the source tree so a source-folder accident cannot
  destroy them.
- Do not store the database password in any committed file; use `PGPASSWORD`
  only transiently in a shell.
